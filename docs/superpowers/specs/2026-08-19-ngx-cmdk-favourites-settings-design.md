# ngx-cmdk: Favourites & Settings — Design

**Date:** 2026-08-19
**Status:** Approved, pending implementation plan

## Summary

Adds the last two features shown in the original reference screenshot but not
yet built: **Favourites** (a small, user-managed list of `{ label, path }`
shortcuts a person navigates to often) and a **Settings** panel — a second
view inside the same command palette, opened with `,` — where Favourites are
added, removed, and reordered.

Both pieces follow this library's established "opt-in costs nothing"
philosophy: with neither `favouritesStorageKey` nor `recentSearchesStorageKey`
configured, the Settings panel does nothing at all (the `,` shortcut is
inert), and with no `favouritesStorageKey` specifically, the Favourites
section — in both the main palette and inside Settings — never appears.

Settings is designed as a small **container**, not something wired
specifically to Favourites: its second section, "Recent searches," surfaces
the "Clear recent searches" action `RecentSearchesService` already exposed
programmatically, giving it a UI home. Each section gates independently on
its own governing config key; Settings itself is reachable only when at
least one section would have something to show.

## Data model & config

```ts
interface CmdkConfig {
  shortcut: string;
  searchTimeoutMs: number;
  recentSearchesStorageKey?: () => string | null;
  favouritesStorageKey?: () => string | null;               // NEW
  navigate?: (path: string) => void | Promise<void>;         // NEW
}

interface FavouriteEntry {
  id: string;      // library-generated, stable identity for move/remove
  label: string;
  path: string;
}
```

- `navigate` mirrors `SearchResult.execute`'s shape exactly
  (`() => void | Promise<void>` there; `(path: string) => void | Promise<void>`
  here) — the library never imports `@angular/router` or any routing
  concept itself. A host app wires
  `navigate: (path) => router.navigateByUrl(path)`.
- `favouritesStorageKey` is independent from `recentSearchesStorageKey` — a
  host app can enable one without the other, or scope them to different
  keys, exactly like the two are independent config knobs today.
- `id` is generated by `FavouritesService` when a favourite is added (never
  supplied by the caller), the same way `Command.id` is auto-generated when
  omitted — it exists so `remove`/`moveUp`/`moveDown` can target a stable
  identity instead of relying on array position or an exact-value match,
  which breaks the moment two favourites share a label.
- No `resultId`/`resolve()` concept here, unlike search results: a
  favourite's `path` already fully describes what selecting it does. There
  is nothing to "resolve" — `path` is a plain string persisted and read back
  as-is.

## `FavouritesService`

```ts
@Injectable({ providedIn: 'root' })
class FavouritesService {
  readonly favourites: Signal<readonly FavouriteEntry[]>;  // order = shortcut order, capped at 9
  add(label: string, path: string): void;                   // no-op: no key, no room, or empty label/path
  remove(id: string): void;
  moveUp(id: string): void;                                  // no-op if already first
  moveDown(id: string): void;                                // no-op if already last
  clear(): void;
}
```

Lives at `projects/ngx-cmdk/src/lib/favourites/favourites.ts`, its own
folder alongside `command/`, `search/`, `palette/`, `config/`, `issue/`, and
`shortcut/`.

This service reuses, wholesale, the persistence/reactivity design already
built and hardened for `RecentSearchesService`:

- An internal writable signal holding the currently-loaded list, kept in
  sync with the *current* value of `favouritesStorageKey?.()` via a
  constructor `effect()` — so a host app whose callback closes over a
  reactive signal (e.g. `() => authService.userId() ? '...' : null`) sees
  the list reactively collapse to `[]` the instant the key becomes
  unavailable, the same guarantee `RecentSearchesService.recent()` makes.
- Every mutator (`add`, `remove`, `moveUp`, `moveDown`, `clear`) independently
  re-syncs to the current key before acting — not just the constructor
  effect — so correctness never depends on when Angular happens to flush
  that effect, exactly the fix applied to `RecentSearchesService.clear()`
  during the Recent Searches implementation.
- `localStorage` access is wrapped against a thrown `SecurityError`
  (storage-blocked iframes, sandboxed frames) degrading to "no persistence"
  rather than crashing the palette.
- Persisted JSON is validated per-element on read, not just checked for
  `Array.isArray` — a malformed entry is dropped rather than trusted, the
  same hardening added to `RecentSearchesService.readFromStorage()`.

Differences from `RecentSearchesService`:

- `add()` enforces a hard cap of 9 entries (`favourites().length >= 9` makes
  a further `add()` call a silent no-op) — this cap exists because position
  determines shortcut (see below), and there are only 9 single-digit keys.
  There is no "evict oldest" behavior here (unlike Recent Searches' cap):
  a full favourites list simply refuses new entries until the user removes
  one, since — unlike recents — every entry here was deliberately added by
  the user and none of them should be silently discarded.
- `add()` trims and requires both `label` and `path` to be non-empty after
  trimming; either being empty/whitespace-only is a silent no-op.
- `moveUp(id)`/`moveDown(id)` swap the target entry with its neighbor in the
  ordered list; calling either at a list boundary (`moveUp` on the first
  entry, `moveDown` on the last) is a silent no-op.
- `clear()` exists from day one — a "remove all favourites" affordance is an
  obvious companion to per-row removal, and it's effectively free given the
  shared machinery.

## Digit shortcuts: `mod+1` … `mod+9`

A favourite's position in the list directly determines its keyboard
shortcut: the 1st favourite is `mod+1`, the 2nd is `mod+2`, and so on up to
the 9th at `mod+9`. This is why reordering matters functionally, not just
cosmetically, and why the cap is exactly 9.

**Firing the shortcut** reuses the exact mechanism Command shortcuts already
use — `parseShortcut`/`matchesShortcut` from `shortcut.ts` — computing each
favourite's shortcut as `parseShortcut('mod+' + (index + 1), isMac)` and
checking incoming keydown events against it. Because a modifier is always
required, **there is no ambiguity with typing** — holding Cmd/Ctrl while
pressing a digit never inserts a character into a focused text field, in any
browser. This is a deliberate correction from an earlier "bare digit,
query-must-be-empty" design: a bare-digit approach breaks the moment a user
starts a query that legitimately begins with a digit (an order number, a
ticket ID) — the very first keystroke of such a query would be swallowed as
a favourite-shortcut trigger instead of appearing in the input. Requiring a
modifier removes this class of conflict entirely, and means a favourite's
`mod+N` shortcut fires **regardless of current view/query/scope state**,
exactly like a Command's shortcut already does while the palette is open —
not just when the Favourites section happens to be visible.

The integration point is `CmdkPaletteComponent.onKeydown()`'s existing
`default` case, which today only checks `registry.matchShortcut(event)`.
It gains a second check against the palette's computed favourite shortcuts,
calling `config.navigate(favourite.path)` on a match. Digit keys already
fall into this `default` branch today, since no named `case` in the
existing `switch (event.key)` matches them.

**Reserving the digit namespace for Commands.** Since digits — modified or
not — now exclusively mean "favourite" everywhere in this library,
`projects/ngx-cmdk/src/lib/shortcut/shortcut.ts`'s validation changes so a
Command's shortcut key must be `a`–`z`; `0`–`9` is rejected outright, with or
without a modifier. `registry.register({ shortcut: 'mod+1', ... })` now
throws at registration time — the same fail-fast convention already applied
to duplicate `id`/`shortcut`/provider `key`. This is the one place this
feature changes previously-valid behavior for existing consumers: a Command
shortcut like `"mod+1"`, valid today, becomes a registration-time error.
`provideCmdk()`'s own `shortcut` field (the palette's open-shortcut) is
unaffected by this specific rule change in practice, since nobody
reasonably configures a bare digit as the palette's own open-shortcut — but
the same validation function now applies there too, for consistency.

**Displaying the hint.** In the browse-view (empty query, unscoped) list,
each favourite row shows its shortcut formatted via the existing
`formatShortcut()` helper — `⌘1` on Mac, `Ctrl+1` elsewhere — styled
identically to a Command's `.cmdk-shortcut` hint span. The hint is
display-only in that view; it does not gate whether the shortcut itself can
fire (which, as above, works from anywhere the palette is open).

## Where Favourites appear in the main palette

Favourites render as a new section below "Actions," visible only in the
same state Recent Searches already uses: empty query, nothing scoped. This
mirrors Recent Searches' precedent exactly — a plain list, not routed
through `fuzzySearch`/`groupMatches`, never findable by typing a query. The
reasoning is the same one that applies to the digit-shortcut hints: a
favourite's identity in this view is tied to its position, and position
only means something in the stable, unfiltered browse list.

Favourites fold into the palette's existing unified `selectedIndex`
keyboard-navigation mechanism, the same way Recent Searches did — prepended
into the selectable list (after Recent Searches, before Commands, matching
the original reference screenshot's ordering: chips → Recent searches →
Actions → Favourites). Enter/click on a favourite calls
`config.navigate(favourite.path)` the same way `mod+N` does.

## The Settings panel

**Opening it.** `CmdkPaletteComponent` gains
`protected readonly settingsOpen = signal(false);`. Pressing `,` while the
query is empty and nothing is scoped sets it `true` — the same
query-must-be-empty gating already established for reserved single-key
affordances in this palette (mirroring how `Backspace` only de-scopes when
the query is also empty). A bare `,` requires no modifier because, unlike
digits, it is a rare leading character of a real search query, so the
existing empty-query gate is sufficient here — this is a narrower,
already-proven pattern, not the same conflict digits had.

**Closing it.** From within Settings, pressing `,` again, pressing
`Escape`, or clicking the footer's "CLOSE SETTINGS" button all return
`settingsOpen` to `false` — back to the list view, not closing the whole
palette. A second `Escape` from the list view closes the palette itself,
matching the general convention that `Escape` closes the innermost overlay
first.

**Visibility gate.** The `,` shortcut (and anything Settings would show)
only does something if at least one of `favouritesStorageKey` /
`recentSearchesStorageKey` is configured. With neither set, `,` is
completely inert — consistent with the hard-gate philosophy already applied
everywhere else in this library.

**Focus.** Opening Settings moves focus to the add-favourite Label input,
mirroring how opening the palette itself focuses the main search input.

**Internal structure.** Rather than growing `cmdk-palette.ts`/`.html`
further, the Settings view's markup lives in a new, library-internal
component — not exported from `public-api.ts` — `CmdkSettingsPanelComponent`
in `projects/ngx-cmdk/src/lib/settings/`, rendered from `cmdk-palette.html`
only when `settingsOpen()` is true. It injects `FavouritesService` and
`RecentSearchesService` directly (both `providedIn: 'root'`; no
`@Input`/`@Output` plumbing needed for the data itself) and emits a single
`close` output the parent listens to, wiring it to the same
"return to list view" path as `,`/`Escape`.

Its content, top to bottom:

1. **Favourites section** (rendered only if `favouritesStorageKey` is
   configured): one row per favourite, in shortcut order — label input,
   path input, move-up button, move-down button, and a remove (×) button.
   Below the list, a trailing add-row: empty Label/Path inputs and a submit
   affordance, disabled until both fields are non-empty (after trimming).
   Submitting calls `FavouritesService.add()` and clears both inputs so
   another entry can be added immediately. Once 9 favourites exist, the
   add-row is replaced with a short message explaining the limit has been
   reached, rather than staying visible in a permanently-disabled state.
2. **Recent searches section** (rendered only if `recentSearchesStorageKey`
   is configured): a heading and a single "Clear recent searches" button
   calling `RecentSearchesService.clear()`.
3. **Footer:** a "CLOSE SETTINGS" button and the `,` hint, both routing to
   the same close path.

**Keyboard isolation.** Once Settings has its own text inputs (Label/Path)
and buttons, its keyboard handling cannot share `onKeydown()` with the list
view — that handler runs on any keydown bubbling up through `.cmdk-panel`,
and its existing cases would misbehave against Settings' own inputs:
`ArrowUp`/`ArrowDown` would hijack text-cursor movement inside a focused
Label/Path field instead of moving the caret; `Enter` would try to execute
whatever the list view's `selectedIndex` happens to still point at (a stale,
meaningless value in Settings mode) instead of submitting the add-favourite
row; `Tab` would yank focus back to the main search input instead of moving
between Label and Path. To avoid all of this, `CmdkSettingsPanelComponent`'s
root element has its **own** `(keydown)` handler that calls
`stopPropagation()` — the two view modes' keyboard handling are fully
decoupled, one never falling through to the other, rather than the list
view's handler needing to grow settings-mode-aware branches.

## Error handling

- **`navigate()` failure** (throws synchronously, or returns a rejected
  `Promise`): the same dual-channel pattern used everywhere else in this
  library — `console.error` plus a new `CmdkIssue` variant
  `{ source: 'favourite-navigate'; label: string; path: string; error: unknown }`.
  Neither the palette nor the Settings panel does anything further (no
  retry, no built-in toast) — consistent with "the consumer decides what
  'failed' looks like, via `onIssue()`."
- **`FavouritesService`'s storage boundary** logs via `console.warn` only
  (blocked storage, malformed persisted data) — no `CmdkIssue` variant,
  since there's nothing actionable for a consumer to react to, matching the
  precedent already set for `RecentSearchesService`.
- **Add-form validation is silent, not error-reported**: an empty
  label/path just leaves the submit affordance disabled; reaching the
  9-favourite cap replaces the add-row with an explanatory message rather
  than a button that silently no-ops when clicked.

## Testing strategy

- **`shortcut.ts`**: a Command shortcut using any digit (`"1"`, `"mod+1"`,
  `"mod+shift+1"`) is rejected at registration time; `a`–`z` keys are
  unaffected; `provideCmdk()`'s own shortcut validation uses the same
  updated rule.
- **`FavouritesService`**: hard-gated on `favouritesStorageKey` (no key →
  `favourites()` is `[]`, every mutator a no-op); `add()` no-ops on
  empty/whitespace label or path (after trimming); cap at 9 (a 10th `add()`
  call is a no-op, existing 9 unchanged); `remove`/`moveUp`/`moveDown`
  behave correctly including at list boundaries; persistence round-trips
  through real `localStorage`; malformed persisted data is filtered
  per-element without throwing; a blocked/throwing `localStorage` degrades
  gracefully; reactive key-change (collapsing to `[]`, picking up a
  different key's data) mirrors the already-proven `RecentSearchesService`
  tests; `clear()` empties both memory and storage.
- **`CmdkPaletteComponent`**: `,` opens Settings only when the query is
  empty and unscoped, and does nothing with neither storage key configured;
  `mod+1`…`mod+9` navigate the correct favourite regardless of current
  view/query/scope state; the Favourites section renders below Actions only
  in the browse view, with correctly-formatted shortcut hints, and folds
  into the existing `selectedIndex` mechanism; a `navigate()` throw/rejection
  reports through `CmdkIssueService` with the `favourite-navigate` shape and
  does not crash or leave the palette in a broken state.
- **`CmdkSettingsPanelComponent`**: each section renders only when its
  governing key is configured; the Settings-opening gate itself requires at
  least one of the two keys; typing into Label/Path inputs doesn't trigger
  list-mode side effects (Arrow keys move the text cursor normally, Enter
  doesn't try to execute a stale `selectedIndex`, Tab moves between the
  panel's own fields) — proven by asserting the list-view's `onKeydown()`
  effects don't fire while Settings is open; add-row validation and
  disable-at-cap; move-up/move-down actually change future shortcut
  assignment (moving a favourite into position 1 makes `mod+1` navigate it);
  remove; closing via the footer button, `,`, and `Escape` all return to the
  list view without closing the whole palette.

## Out of scope (for this spec)

- Drag-and-drop reordering — up/down move buttons instead, since this
  library has zero UI-kit dependency and building pointer-based dragging
  from scratch is a substantial, separable piece of work. Worth revisiting
  later if move-buttons prove too clunky in practice.
- Favouriting an existing registered Command directly (e.g. "pin this
  Command") — Favourites are purely user-typed `{ label, path }` pairs
  navigated via the host app's `navigate` callback, not a wrapper around
  `CommandRegistryService.execute()`.
- Any other Settings sections beyond Favourites and Recent-searches-clearing
  (theming, shortcut customization, search-provider preferences) — the
  container is built to make adding more sections straightforward later,
  but none of those are designed or built here.
- More than 9 favourites, or favourites without a keyboard shortcut — the
  cap is exactly 9, tied to the single-digit keyboard range.
- Import/export of a favourites list, or any cross-device sync beyond
  whatever `localStorage`'s natural same-origin behavior already provides.
